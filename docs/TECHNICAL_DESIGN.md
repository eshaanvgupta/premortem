# Technical design — page 1 of 2

NEXORA separates deterministic observations from advisory community judgment. The unit of work is an Action Capsule: a creator-bound action hash, evidence root, simulation hash, bounded public label, open/blind mode, deadlines, quorum and immutable outcome. Full calldata/evidence stays local by default; publishing hashes does not guarantee content availability. Long evidence is not uploaded to an unconsented service.

The action domain includes BSC chain ID, protocol address, creator, target, value, calldata hash, salt, block number/hash and version. This prevents accidental ambiguity between actions and contexts; it does not prove that an off-chain observation is true. The core canonicalizes input and preserves integer wei as strings. At a recorded recent block it checks RPC chain identity, contract code, selector formats, exact call result and gas estimation. Findings expose severity, category, observed condition, evidence, source, rule version, confidence and limitations. Unknown ABI and failed or unsupported calls cannot become a “safe” result. The Future Tree reads these actual findings and review state.

One compact immutable Solidity registry stores capsule metadata and bounded counters. It has no owner, upgrade, custody, token, fee, transfer, approval, cancel or arbitrary-call capability. On mainnet it can only be constructed with the official Agent ID address. Each substantive holder action uses the actual sender's `balanceOf` through a read-only bounded call; failures revert clearly. This trusts the official registry's documented interface, issuer semantics and availability. It does not establish unique real-world persons or replace the competition identity with ERC-8004.

Public capsule lists and timelines work from bounded chain event scans and short on-chain labels without a database or IPFS gateway. Relevant events index capsule and actual actor. Consumers must show scan coverage and finality, verify canonical blocks, invalidate affected cached ranges after reorgs and distinguish pending from confirmed. Dataseed providers may disable logs; fallback capability failures must remain visible. A count computed from incomplete history is only an observed lower bound.

# Technical design — page 2 of 2

Independent reviewers choose verdict, confidence, evidence digest and risk category. One completed review per account per capsule and no creator self-review are on-chain constraints. Open review is allowed before the room deadline. Blind mode enforces a separate commit interval and reveal interval. The commitment binds chain, protocol, capsule, reviewer, verdict, confidence, evidence digest, category and cryptographically random salt. Only a matching reveal in the valid interval counts. Reviewers must retain the private reveal package; lost salts have no recovery/backdoor.

Finalization is permissionless after the reveal deadline and runs in constant time. Quorum is bounded 2–9. Counted votes include insufficient-evidence votes; approval/rejection needs strictly more than half of all counted votes and sufficient quorum. Ties, missing quorum and absent majority become Inconclusive. Nonrevealed commitments never count. Confidence is descriptive and does not weight votes. The result is frozen, advisory and cannot authorize or execute the original action.

The website has read-only access by default. Injected EIP-1193 wallet behavior is described only for actual supported providers; it is not an Agentic Wallet connector. The Agentic Wallet path exports a narrow typed protocol action file. Inside the user's trusted runtime, the independent local CLI verifies configuration, checks official `baw` Developer Mode, encodes only allowlisted zero-value protocol methods, simulates, previews, displays parsed parameters/risks/authority changes, requests explicit human confirmation and executes only that preview request ID. Disabled/expired modes, failures and unknown schemas block execution. Pending App confirmation is not a receipt and ambiguous execute responses are not retried automatically.

Decision exports carry protocol/chain/deployment identity, capsule/action hashes, review counts/outcome, block and transaction evidence plus off-chain content hashes where available. Independent verification re-fetches successful receipts and canonical event data. This is RPC consistency checking, not a cryptographic light-client proof. A malicious RPC, compromised host/local runtime, colluding eligible accounts, dishonest evidence or unavailable off-chain content remain explicit risks. No model is required, and optional explanation cannot change deterministic facts or authorization.

Release requires actual tests/build evidence, operator-approved deployment, source verification, public hosting/source publication, actual consenting-holder wallet compatibility and meaningful genuine adoption. None is replaced by a local mock or fabricated metric. Mainnet addresses and live participant totals remain unknown until measured; every status surface and submission must preserve that distinction.
