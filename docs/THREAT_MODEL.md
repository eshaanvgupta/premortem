# Threat model

| Threat                                              | Control                                                                                                        | Residual risk                                                                         |
| --------------------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------- |
| Nonholder or claimed representative creates/reviews | Actual `msg.sender` balance check at immutable official registry for each holder action                        | Identity issuer semantics and availability are external dependencies                  |
| Creator boosts its own capsule                      | Creator review/commit/reveal rejected                                                                          | Collusion between distinct eligible addresses remains possible                        |
| Duplicate reviews and count inflation               | One completed review per address; one commitment; missing reveals never count                                  | One wallet does not equal mathematically unique person                                |
| Blind vote replay/equivocation                      | Commitment includes chain, registry, capsule, reviewer, verdict, confidence, evidence/category and random salt | Salt loss or pre-reveal disclosure undermines participation/privacy                   |
| Phase bypass, early finalization                    | On-chain timestamp checks, fixed bounded phase lengths, frozen finalization                                    | Validator timestamp assumptions apply; keep adequate reveal margins                   |
| Gas exhaustion or callback attacks                  | Bounded strings; constant-time counting; identity staticcall gas bound                                         | External identity upgrades may break compatibility; spam still creates public records |
| Fake facts or misleading consensus                  | Evidence hashes and provenance; explicit uncertainty; advisory outcome                                         | The contract cannot establish substantive evidence quality or objective truth         |
| Hostile token calldata/metadata                     | Strict address/hex validation; selector confidence limits; escaped text                                        | Selector spoofing and malicious contract behavior require deeper independent review   |
| Website compromise / address substitution           | Exact destination/method/hash shown; local registry configuration checked; wallet preview                      | User must verify deployment source/address; host can alter delivered frontend         |
| Wallet credential theft                             | No hosted QR, pairing codes, secrets, sessions or backend signing                                              | User's trusted local environment and official wallet CLI must remain uncompromised    |
| Prompt/CLI injection                                | Treat evidence as data; shell-free argument arrays; no auto-confirm flag; terminal sanitization                | A compromised local CLI executable is outside this trust boundary                     |
| RPC omission/reorg/count forgery                    | Confirmations, block-hash reconciliation, bounded scans, explicit partial-history status                       | Provider consensus is not independently proven; archival data may be unavailable      |
| Evidence disappearance                              | Original content stays local; on-chain hashes/short labels persist                                             | Content hash does not guarantee off-chain availability or pinning                     |

Assets at risk are review integrity, privacy of unpublished action details and salts, user gas, and user trust. The registry is not designed to hold assets. Consensus attacks do not grant a method to transfer assets because no such method exists. Nothing prevents a user executing an action outside NEXORA; review outcomes cannot authorize that action.
